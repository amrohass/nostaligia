## 0 · Signup blocked — diagnosed, one half fixed, the other half is (1) above

**The limiter is named, not inferred.** A real signup against the live Auth endpoint:

    HTTP/1.1 429 Too Many Requests
    x-sb-error-code: over_email_send_rate_limit
    {"code":429,"error_code":"over_email_send_rate_limit","msg":"email rate limit exceeded"}

That is GoTrue's **email-send** cap. What it is not, each ruled out by measurement rather
than by elimination:

- **Not a per-IP or per-request limit.** Six rapid `POST /auth/v1/recover` calls in a row
  all answered `200`. `over_request_rate_limit` never appeared.
- **Not a Cloudflare WAF rule.** The refusal carries `x-sb-error-code` from GoTrue itself,
  not a Cloudflare block response, and the repository contains no WAF rule for this path.
- **Not signups being disabled.** `GET /auth/v1/settings` reports `disable_signup: false`,
  `email: true`, `mailer_autoconfirm: false` — so every signup sends a confirmation email,
  which is what meets the cap.
- **Not this week's test volume in the way it looked.** `auth.users` shows 11 rows, newest
  **29 Aug 22:21 UTC**, and 7 of those were created inside seven minutes on 28 Aug at
  `mail.example.com` — the harness, via the admin API, which sends no mail. Only a handful
  of signups have ever gone through the public form.

**Is it a real bug or expected behaviour?** Expected behaviour of a configuration that is
wrong for this system. The cap is **project-wide, not per-user**: with Supabase's built-in
sender it is a very small number of messages per hour across *all* visitors. So:

> **A genuine new member absolutely hits this under normal use** — not because they did
> anything, but because somebody else signed up in the same hour. For an archive expecting
> "tens of thousands of users worldwide" (§1) this is a launch blocker, and it is invisible
> in testing because a solo maintainer rarely trips a shared hourly cap.

**FIXED this session — the message.** `over_email_send_rate_limit` and
`over_request_rate_limit` were mapped to the same string, so the site told a first-time
visitor *"محاولات كثيرة خلال وقت قصير"* / "Too many attempts just now" for a cooldown that
was not theirs and that waiting would not always clear. Split into `auth.err.mailLimit`,
which says it is our sending limit and not something they did. `frontend-auth-test.mjs`
pins the two 429s as a **pair** so a later tidy-up cannot merge them back; verified
discriminating by reverting the mapping and watching the assertion go red.

**GATED — the cause.** Configure custom SMTP and raise the auth email rate limit. Decision
(1) above.

**Found on the way, and it is the more serious half.** GoTrue **captcha protection is
disabled**:

    POST /auth/v1/token?grant_type=password, no captcha token          → 400 invalid_credentials
    POST /auth/v1/token?grant_type=password, invalid captcha token     → 400 invalid_credentials

An invalid token is accepted and ignored — it never reaches a verifier. `auth.js` fetches a
Turnstile token and sends it in `gotrue_meta_security.captcha_token`, and nothing checks it,
so §6's "Turnstile on signup" is currently client-side only, which §5 says is not a guard at
all. Two consequences: `/signup` is an unauthenticated, unthrottled way to make the project
send mail (which is the same faucet as (1), from the other end), and the abuse ceiling §6
builds in four layers has one layer missing here. Decision (2). Note the upload path is
**not** affected — `request-upload` verifies Turnstile server-side in the Edge Function.

**Not measured:** whether custom SMTP is configured, and the exact configured threshold and
window. Both live in Authentication → Rate Limits / SMTP in the dashboard, which needs a
Management API token I do not have; enumerating the CLI's credential store was refused by
the sandbox and I did not work around it.

### The pgTAP suite against the deployed database — the main M0 result

**New tool: `scripts/pgtap-deployed.mjs`** (+ `scripts/lib/pgtap-tap.mjs`). Runs every test
file against the hosted database inside its own rolled-back transaction. `--tap` rewrites
each top-level `SELECT` into an `INSERT` so the whole TAP stream returns as one result set —
without it the Management API hands back only the last statement's rows, and pgTAP 1.3 keeps
no per-assertion table, so you can learn *that* a file is red and never *which* assertion.

It was proved to discriminate before being trusted, with two controls: a file with a
deliberately false assertion reports red, **and** a file that stops short of its own `plan()`
reports red *even though its failure count is legitimately zero* — the reading that would
otherwise turn a file dying at assertion 3 of 17 into a pass.

**Result: 34 of 35 files green. 643 assertions ran of 643 declared; 640 pass.**

Seven files were red on the first run. **None was a product defect.** Every one was the
suite assuming an empty database — which is the real finding, because it means the suite

### The exit criterion, and the ambiguity in it

The 29 Aug audit could only say `originals/*` 404s through the CDN, "which is consistent with
correct bucket bindings and also consistent with the object simply not existing". That is the
whole problem: the reassuring measurement and the alarming one look identical from outside.
**`scripts/r2-invariants.ts`** reads both ends — the private bucket over a signed request, the
public one over the CDN — and all 41 checks hold across 5 masters and 10 derivatives:

- every master **exists** in `originals/` (signed `HEAD` 200), **byte-for-byte** its declared

- every master is **404 through the CDN**;
- every derivative is **200 through the CDN** with `Content-Length` equal to

With a **CONTROL** that makes the 200s mean something: a key that certainly does not exist

is there" is a measurement rather than an artefact of a malformed request.

### FIXED — Turnstile could hang the sign-in and upload dialogs forever

Found on the way to that measurement, and it is not an automation artefact.
`TURNSTILE.mount().token()` pushed a waiter that **only the success callback ever resolved**:
`error-callback` set `current = null` and returned, `remove()` discarded the array, and a
widget that rendered and then said nothing was not handled at all. There was no deadline —
`whenReady`'s 6-second timeout covers only the *script* arriving. §6 puts Turnstile between
the member pressing the button and anything happening, so all three paths present as one
thing: the dialog sits on its working state forever, with no message and nothing to retry.

Now `error-callback` and `timeout-callback` reject pending waiters, `remove()` rejects rather
than drops, and `token()` carries a 30-second deadline — generous, because an interactive
challenge is not a refusal, but a ceiling on silence. `unavailable` is deliberately **not** set
on an error, so `reset()` can still re-arm. Five assertions added with a CONTROL that the
happy path is untouched; verified discriminating against the old file, where the control still
passes, one assertion fails, and one **crashes because the old code never registered a
`timeout-callback` at all**.

### The audit trail (§4), on the deployed database

A moderator approving a post writes **one `moderation_actions` row and one `audit_log` row**,
both naming the acting moderator, and the approval's audit row carries **both `before` and
`after`** (`post.status.approved.self`). `07_triggers` pins the dual write permanently and is
green against deployed.

**The known gap is confirmed and now pinned by measurement:** an admin saving site copy
through `save_content_block` writes an `audit_log` row and **no `moderation_actions` row**,
because `moderation_actions.target_id` is `uuid NOT NULL` while `content_blocks` is keyed
`(key, locale)`. That is decision (3) at the top of this document. One correction to the
handoff, which said `audit_log`'s "`target_id` is nullable and `target_type` is text":
`target_id` is **`uuid`, nullable**; it is `target_type` that is text. The nullability is what
lets 0055 write the row at all, so the conclusion stands.

**A method note, because it cost me two wrong readings in one hour.** My first pass asserted
the wrong JSON keys (`error`/`quota_bytes` instead of `reason`/`over_daily_bytes`) — and the
"CONTROL" beside it, `error is null`, passed **vacuously**, because `error` never exists in
that payload. Then a second probe read the wrong audit row: `now()` does not advance inside a
transaction, so `order by created_at desc limit 1` is nondeterministic between rows written in
the same batch, and it returned `post.create` instead of the approval — which made a correct
`before`/`after` look like a §4 violation. Both were my errors, not the system's, and both are
the exact defect class this repository keeps finding in its own tests.

### The single-writer lock, under genuine concurrency

The 29 Aug audit recorded the lock as "intact, and `publish-race.sh` runs in CI". Against
the deployed system it had **never actually been exercised**: `net._http_response` held 8
dispatches, all `published`, **zero `held`** — publishes take about a second and had simply
never overlapped.

Two things had to be got past to test it properly. Racing two `supabase db query` processes
does not work — the CLI provisions a temporary login role per invocation and concurrent ones
collide with `password authentication failed for user "cli_login_postgres"`. And a tick fired
after the first one finishes is answered `unchanged`, not `held`, which looks like the lock
working and is nothing of the kind.

So: a no-op content change (`update places set name_ar = name_ar`) to make a publish due —
which itself dispatches, via `bump_publish_revision` — and then **three concurrent POSTs
straight at the deployed publisher** while that build was in flight. All three:

    HTTP 200  {"published":false,"reason":"held"}

Four overlapping attempts, and afterwards:

- `active_count = 1` — one active release, `releases_only_one_active` intact under concurrency;
- `pending = false`, reason `unchanged` — **the change was not lost**, which is the half that
  matters. §2's "0042's follow-up collects the rest" is doing its job;
- one new release, `published_responses` 8 → 9.

That is the exit criterion, met on the deployed system rather than in CI.

### A killed build

There is no way to SIGKILL a Supabase Edge Function mid-run from here, so this is **not
directly tested** and is not claimed. What was measured instead is the property the criterion
protects — that the pointer never points at an incomplete tree. **All 20 recorded releases
were fetched and every one is complete** (`index.json`, `content.json`, `feed/page-1.json`

Combined with the `held` result above and `17_publish_lease` / `21_publish_rollback` passing

### Counter baking

The live release showed `69ed30c5` with `likes=0` while the database had `likes=1`. That is
**correct, not stale-by-accident**: the like landed at `18:05:34.79` and the release was built
at `18:05:33.42` — **1.4 seconds earlier**. §2's 20 Aug amendment says only the content branch

## 0 · Signup blocked — diagnosed, one half fixed, the other half is (1) above

**The limiter is named, not inferred.** A real signup against the live Auth endpoint:

    HTTP/1.1 429 Too Many Requests
    x-sb-error-code: over_email_send_rate_limit
    {"code":429,"error_code":"over_email_send_rate_limit","msg":"email rate limit exceeded"}

That is GoTrue's **email-send** cap. What it is not, each ruled out by measurement rather
than by elimination:

- **Not a per-IP or per-request limit.** Six rapid `POST /auth/v1/recover` calls in a row
  all answered `200`. `over_request_rate_limit` never appeared.
- **Not a Cloudflare WAF rule.** The refusal carries `x-sb-error-code` from GoTrue itself,
  not a Cloudflare block response, and the repository contains no WAF rule for this path.
- **Not signups being disabled.** `GET /auth/v1/settings` reports `disable_signup: false`,
  `email: true`, `mailer_autoconfirm: false` — so every signup sends a confirmation email,
  which is what meets the cap.
- **Not this week's test volume in the way it looked.** `auth.users` shows 11 rows, newest
  **29 Aug 22:21 UTC**, and 7 of those were created inside seven minutes on 28 Aug at
  `mail.example.com` — the harness, via the admin API, which sends no mail. Only a handful
  of signups have ever gone through the public form.

**Is it a real bug or expected behaviour?** Expected behaviour of a configuration that is
wrong for this system. The cap is **project-wide, not per-user**: with Supabase's built-in
sender it is a very small number of messages per hour across *all* visitors. So:

> **A genuine new member absolutely hits this under normal use** — not because they did
> anything, but because somebody else signed up in the same hour. For an archive expecting
> "tens of thousands of users worldwide" (§1) this is a launch blocker, and it is invisible
> in testing because a solo maintainer rarely trips a shared hourly cap.

**FIXED this session — the message.** `over_email_send_rate_limit` and

### FIXED — Turnstile could hang the sign-in and upload dialogs forever

Found on the way to that measurement, and it is not an automation artefact.

### The single-writer lock, under genuine concurrency

The 29 Aug audit recorded the lock as "intact, and `publish-race.sh` runs in CI". Against
the deployed system it had **never actually been exercised**: `net._http_response` held 8
dispatches, all `published`, **zero `held`** — publishes take about a second and had simply

Two things had to be got past to test it properly. Racing two `supabase db query` processes
does not work — the CLI provisions a temporary login role per invocation and concurrent ones
collide with `password authentication failed for user "cli_login_postgres"`. And a tick fired
after the first one finishes is answered `unchanged`, not `held`, which looks like the lock
working and is nothing of the kind.

So: a no-op content change (`update places set name_ar = name_ar`) to make a publish due —
which itself dispatches, via `bump_publish_revision` — and then **three concurrent POSTs
straight at the deployed publisher** while that build was in flight. All three:

    HTTP 200  {"published":false,"reason":"held"}

Four overlapping attempts, and afterwards:

- `active_count = 1` — one active release, `releases_only_one_active` intact under concurrency;
- `pending = false`, reason `unchanged` — **the change was not lost**, which is the half that
  matters. §2's "0042's follow-up collects the rest" is doing its job;
- one new release, `published_responses` 8 → 9.

That is the exit criterion, met on the deployed system rather than in CI.

## 0 · Signup blocked — diagnosed, one half fixed, the other half is (1) above

**The limiter is named, not inferred.** A real signup against the live Auth endpoint:

    HTTP/1.1 429 Too Many Requests
    x-sb-error-code: over_email_send_rate_limit
    {"code":429,"error_code":"over_email_send_rate_limit","msg":"email rate limit exceeded"}

That is GoTrue's **email-send** cap. What it is not, each ruled out by measurement rather
than by elimination:

- **Not a per-IP or per-request limit.** Six rapid `POST /auth/v1/recover` calls in a row
  all answered `200`. `over_request_rate_limit` never appeared.
- **Not a Cloudflare WAF rule.** The refusal carries `x-sb-error-code` from GoTrue itself,
  not a Cloudflare block response, and the repository contains no WAF rule for this path.
- **Not signups being disabled.** `GET /auth/v1/settings` reports `disable_signup: false`,
  `email: true`, `mailer_autoconfirm: false` — so every signup sends a confirmation email,
  which is what meets the cap.
- **Not this week's test volume in the way it looked.** `auth.users` shows 11 rows, newest
  **29 Aug 22:21 UTC**, and 7 of those were created inside seven minutes on 28 Aug at
  `mail.example.com` — the harness, via the admin API, which sends no mail. Only a handful
  of signups have ever gone through the public form.

**Is it a real bug or expected behaviour?** Expected behaviour of a configuration that is
wrong for this system. The cap is **project-wide, not per-user**: with Supabase's built-in
sender it is a very small number of messages per hour across *all* visitors. So:

> **A genuine new member absolutely hits this under normal use** — not because they did
> anything, but because somebody else signed up in the same hour. For an archive expecting
> "tens of thousands of users worldwide" (§1) this is a launch blocker, and it is invisible
> in testing because a solo maintainer rarely trips a shared hourly cap.

**FIXED this session — the message.** `over_email_send_rate_limit` and
`over_request_rate_limit` were mapped to the same string, so the site told a first-time
visitor *"محاولات كثيرة خلال وقت قصير"* / "Too many attempts just now" for a cooldown that
was not theirs and that waiting would not always clear. Split into `auth.err.mailLimit`,

discriminating by reverting the mapping and watching the assertion go red.

**GATED — the cause.** Configure custom SMTP and raise the auth email rate limit. Decision
(1) above.

**Found on the way, and it is the more serious half.** GoTrue **captcha protection is

### FIXED — Turnstile could hang the sign-in and upload dialogs forever

### The single-writer lock, under genuine concurrency

The 29 Aug audit recorded the lock as "intact, and `publish-race.sh` runs in CI". Against
the deployed system it had **never actually been exercised**: `net._http_response` held 8
dispatches, all `published`, **zero `held`** — publishes take about a second and had simply
never overlapped.

Two things had to be got past to test it properly. Racing two `supabase db query` processes
does not work — the CLI provisions a temporary login role per invocation and concurrent ones
collide with `password authentication failed for user "cli_login_postgres"`. And a tick fired
after the first one finishes is answered `unchanged`, not `held`, which looks like the lock
working and is nothing of the kind.

So: a no-op content change (`update places set name_ar = name_ar`) to make a publish due —
which itself dispatches, via `bump_publish_revision` — and then **three concurrent POSTs
straight at the deployed publisher** while that build was in flight. All three:

    HTTP 200  {"published":false,"reason":"held"}

Four overlapping attempts, and afterwards:

- `active_count = 1` — one active release, `releases_only_one_active` intact under concurrency;
- `pending = false`, reason `unchanged` — **the change was not lost**, which is the half that
  matters. §2's "0042's follow-up collects the rest" is doing its job;
- one new release, `published_responses` 8 → 9.

That is the exit criterion, met on the deployed system rather than in CI.

### A killed build

There is no way to SIGKILL a Supabase Edge Function mid-run from here, so this is **not
directly tested** and is not claimed. What was measured instead is the property the criterion
protects — that the pointer never points at an incomplete tree. **All 20 recorded releases
were fetched and every one is complete** (`index.json`, `content.json`, `feed/page-1.json`
all 200), including all 13 that predate this session. So no partial release has ever been
recorded, and rollback — which is a flip back to one of these — cannot land on a broken one.
Combined with the `held` result above and `17_publish_lease` / `21_publish_rollback` passing
against the deployed database, that is as close as this environment gets.

### Takedown — timed, on the real path

`scripts/takedown-probe.ts`. Takedown is irreversible, so rather than destroy real content to

reaches a release, and there would be nothing to redact), and takes **that** down through the
real deployed function with a real moderator's token.

    takedown responded 207 in 2114 ms
    removed: item/…/index.html, originals/…/master.bin, …/display.webp, …/thumb.webp

| **total elapsed** | **2.9 s**, against §8's 60 s |

Objects were asserted **present** before the timing began, so "gone in 2.9 s" is not a

**`CLOUDFLARE_ZONE_ID` / `CLOUDFLARE_PURGE_TOKEN` are still unset**, confirmed by the function

### Counter baking

### FIXED — every account now has a profile (0057)

`public.profiles` was empty while `auth.users` held 11 rows. No signup path, client or
trigger, had ever created one — in any milestone. So §7's "handle is user-chosen and
mandatory, avatar mandatory" was unimplemented end to end: every byline rendered as "A

`reserved_handles` and the whole handle apparatus (0002's `normalized_handle` /
`is_allowed_handle`, 0004's reserved trigger, 0051's tombstone trigger) existed and had

**0057 adds `ensure_profile(uuid)` and an `AFTER INSERT` trigger on `auth.users`**, plus a
backfill for the accounts that predate it — both through the same function, because a bulk
INSERT in the backfill would have been a second copy of the handle rule and two copies drift.

Three decisions worth stating:

- **The handle carries nothing about the person.** `member_` + 12 random hex. Not the email
  local part (§7: emails are never published, and a handle is published), and **not derived
  from the account id either** — the id is the author key, so a handle that is a pure
  function of it turns every byline into a lookup into the contribution history §7 names as
  the de-anonymisation vector. It satisfies `is_allowed_handle` by construction rather than
  by luck: 19 chars, single-script lowercase Latin plus digits, a letter guaranteed by the
  prefix, one underscore that is neither leading, trailing nor doubled.
- **`avatar_path` stays NULL, and that IS the generated avatar.** 0004 already says so —
  "not NOT NULL here because the generated default is derived from the id at render time" —
  and `public.js` already renders it from the first character of the handle on a derived
  tone. Nothing to write. The test pins the NULL so that "mandatory avatar" is never
  satisfied later by storing a path to a file nobody made.
- **Failure is loud.** Five attempts, then `RAISE`, and the signup fails. An account with no
  profile is precisely the silent half-state that produced this migration; swallowing the
  error to let the signup through would recreate the bug deliberately.

`35_provision_profile.test.sql`, 12 assertions, green against the deployed database. Its
first assertion is the one that would have caught the original bug and is deliberately about
the **whole database** rather than a fixture — *every* account has a profile — because every
existing profile test built its own fixtures by hand, which is exactly the shape that hides
a missing trigger.

### The privilege sweep — systematic this time, and it found no drift

0056's bug was found by accident. Repeated deliberately across **every** table and **every**
function in `public`, for `anon` and `authenticated`, at **table level and column level** —
the second of which matters: `has_table_privilege` does not see column grants, and this
schema uses them heavily, so a sweep reading only the first reports a locked door on an open
table. My first pass made exactly that mistake and showed almost every table as `-`.

**Tables — 18 of them, and the picture is clean:**

- **`anon` holds nothing on any table.** Not one privilege, table or column. §2's "zero
  database reads for public visitors" is enforced at the grant level, not merely by RLS.
- **RLS is enabled on all 18.**
- `authenticated`'s column-scoped grants match 05_matrix exactly, and the governance tables —
  `publish_hold`, `publish_lease`, `publish_revision`, `releases`, `reserved_handles`,
  `upload_quota`, `user_roles` — grant it **nothing**.

**Functions — 77, of which 33 were anon-executable.** Each was *called*, as `anon`, on the
deployed database, rather than reasoned about:

- **~24 are trigger functions and PostgreSQL refuses them outright** — `0A000 trigger
  functions can only be called as triggers` — whatever the grant says. Left alone
  deliberately: revoking would tidy a door with no wall behind it across two dozen functions.
- The plain helpers anon can genuinely call (`is_admin`, `authz_role`, `strip_bidi`,
  `normalized_handle`, `is_allowed_handle`, `fuzz_location`) return the caller's own role or
  transform a value handed to them. `fuzz_location` is a documented grid snap and therefore
  many-to-one — calling it reveals nothing the published point does not already.
- **Every anon-executable function matched the matrix pinned in `16_function_grants`. There
  is no drift.**
